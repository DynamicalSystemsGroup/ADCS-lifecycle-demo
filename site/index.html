The example

A geosynchronous communications satellite has an attitude determination and control system (ADCS): a PD controller whose two gains, Kp and Kd, are the design. One system-level requirement, REQ-001, says the pointing error must settle within 0.1° within 120 seconds of a slew. Several kinds of evidence speak to it: a symbolic estimate (SymPy), a torque-limited simulation (SciPy), model checking (z3) and the model's own simulation. They don't always agree. At one design the linear estimate says 105 s, and the simulation misses the limit by half a second. A qualified engineer has to judge whether the requirement is satisfied, and say why, on the record.

The take-away

A tool says pass. A person says satisfied.

The tool produced a formal result about the model. The human attestation is about the system the model represents. Bridging the two is where systems engineering practice meets software engineering agility.

  1. Requirements declare behavioral envelopes. A system-level requirement states ranges of acceptable behavior, under stated operating assumptions. Without that specification, "working as intended?" has no answer. Every automated system needs a behavioral envelope.
  2. Every kind of evidence has a blind spot. Model checking, simulation, symbolic analysis and tests each cover something and miss something. None of them is the spacecraft. Contradictory evidence is expected, not a failure of the process.
  3. Continuous analysis, continuous publication (CA/CP). Every design change re-runs the analyses and republishes the model, as CI/CD does for code. Automation alone is an open loop. A qualified engineer closes it, and their judgment, with rationale, becomes part of the model.

This is how engineering delivers trusted and trustworthy systems, despite an incomplete and uncertain world.

How open source fits into engineering

Engineering rests on slow, stable standards, and accountable organizations sit on top. Open-source software is the layer in between: it carries the standards into code anyone can build on. The arrows run up, and the organizations feed back into every layer below them.

In this demo, the standard is SysML v2. OpenSysML and sysml-toolkit implement it as open-source software, and OpenMBEE's Flexo MMS stores models through the standard SysML v2 API.

The DEER framework

Declaration, Execution, Evidence, Realization. Four layers of an engineering record, each implemented and stored in its own way. Together they keep the computational record reproducible, so that the evidence about the engineered system can be trusted.

LayerWhat it holdsImplemented asStored inIn this demo
Declarationarchitecture and requirementsSysML v2Flexo MMSsatellite.sysml, authored and evaluated with OpenSysML
Executionscenarios, behavioral modeling and analysis pipelinessoftwarea Git repoSymPy, NumPy/SciPy, z3 and the model's own simulation
Evidencedata generated from measurements, simulations and analyses executeddatasetsappend-only databasescarried in the model commits, each tagged with its Git SHA
Realizationcloud infrastructure and Docker imagesbuild artifactsan artifact registrya reusable Docker image and a locally hosted Flexo service

Two realizations are worth keeping apart. One is the realization of the computational materials: the images and services the analysis runs in, which is what this layer covers. The other is the engineered artifact itself, the satellite that gets built and flown. The model is not the system.

For how a compute run is authorized, built and verified, each step pinned to content hashes and recorded so an outside auditor can replay it, see Governed Compute, End to End.

From CI/CD to CA/CP

Engineering at the speed of software. The two loops have the same steps. Automation alone is an open loop, and a person closes it: first for software, then for engineering. In CI/CD a red check blocks the merge. In CA/CP contradictory evidence is expected, and the engineer's judgment, with rationale, becomes part of the model.

CI/CD, with pull requestsCA/CP: continuous analysis, continuous publication
commit and push a change on a branchrevise the design (Kp, Kd)
CI builds and tests, automatedre-analysis, automated: several kinds of evidence
status checks: a red check blocks the mergeevidence concurring or contradictory: disagreement is expected
a reviewer approves, with commentsa qualified engineer judges, with rationale
the approval is recorded, then deployedthe attestation is recorded in the model and republished

Two audiences, one example

This repository is a running workspace: the same satellite and requirement, built anew for each venue, and every version stays runnable. The two big talks are duals of each other.

For systems engineers, about open-source software: how a vendor-neutral, open-source spine (RDF standards, Python, Flexo MMS) keeps evidence and judgment traceable across heterogeneous tools.
